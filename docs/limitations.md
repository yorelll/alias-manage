# Limitations

- PowerShell 5.1 and PowerShell 7.0–7.2 may reconstruct native command arguments differently from PowerShell 7.3+; the CLI does not use string evaluation to bypass this host limitation. Exact argv preservation is guaranteed at the Alias Manager structured-array boundary; host-native reconstruction remains an expected limitation for affected shapes.
- The argument boundary matrix covers empty strings, spaces, quotes, backslashes, Unicode, wildcards, fixed/user/middle `{{args}}`, working-directory/environment metadata, Python/PowerShell/JAR/native target types, and Batch/CMD metacharacter rejection. Fixtures are CI-only and do not print environment secrets.
- Batch/CMD targets are subject to a second command-line parser; dangerous metacharacters are rejected by the structured executor rather than reinterpreted through a shell string.
- `.bat` and `.cmd` invoke a second parser and require separate escaping.
- Aliases are not recursively resolved.
- Definitions are intended for interactive shells.
- AllSigned and ConstrainedLanguage environments are not supported by the MVP.
- Alias names are globally unique; different meanings per Shell are not supported.
- Filesystem reliability is conservative: known local Linux filesystems use WAL, known network/remote mounts use DELETE fallback, and unknown or Windows ACL cases remain explicitly unverified rather than being treated as safe.
- Windows ACL writable-path detection is intentionally reported as unknown until a verified native ACL boundary is available; unknown paths must not receive a safety grant.
- Syntax checking is best effort. Generated Bash/Zsh files are checked with `bash -n` / `zsh -n` and PowerShell files with the host parser only when that interpreter is present and usable (a health probe must succeed). If the interpreter is missing or unusable (for example a WSL launcher stub on Windows), the check is a documented no-op and the file is accepted unvalidated. Passing a syntax check does not prove that an alias becomes effective in a live Shell.
- PowerShell parser diagnostics are locale-dependent. The syntax probe forces UTF-8 console output to avoid mojibake, but the message language follows the host UI culture and may appear in en-US or another locale. Tests assert readable text, not a specific localized wording.
- `--no-color` and `--verbose` are accepted but currently reserved no-ops. `get` always prints a Rust debug representation and ignores `--format`.
- 以 `__aliasmgr_` 开头的别名名称（不区分大小写）保留给生成的限行守卫内部，校验会拒绝，避免用户别名覆盖 PowerShell 的路径规范化辅助函数。
- 限行只检查调用时的当前工作目录，是防护栏而非沙箱。命令本身仍可切换目录或访问任意绝对路径；直接按路径调用生成脚本、修改生成文件或绕过 Shell 函数都可绕过。检查与执行之间当前目录仍可能变化（例如命令内部或并发 Shell 操作）。失效的配置目录会被跳过：只含失效目录的白名单会拒绝所有执行；非文件系统当前位置（如 `HKLM:\`）会被直接拒绝。
- 限行目录必须是当前平台认定的绝对路径（`Path::is_absolute`）；在 Windows 上导入 Linux 风格的 `/srv/...` 路径会被拒绝，反之亦然。导入时整条记录会被跳过（fail-closed），不会悄悄去掉限制后导入。
- 限行路径在 CLI、GUI、导入和服务层都会去除首尾空白、丢弃空项并去重；校验作为最后防线拒绝任何仍带首尾空白的路径。
- PowerShell 的符号链接/联接点解析依赖 `DirectoryInfo.ResolveLinkTarget`（.NET 6+）或 Win32 `GetFinalPathNameByHandleW`（Windows PowerShell 5.1）。在 ConstrainedLanguage 或 `Add-Type` 被阻止时会回退到词法路径，此时联接点可能绕过或造成误拒，文档不保证该环境下的真实路径解析。
- 限行 PowerShell 包装器是高级函数，因此 PowerShell 公共参数（如 `-Verbose`、`-ErrorAction`）会被包装器消费，不会传给目标命令。未限行别名不受影响。拒绝时使用 `$PSCmdlet.WriteError`，错误输出格式可能包含 PowerShell 的类别信息而非单行文本。
- Git Bash/Cygwin 上，限行使用 `cygpath -m` 统一当前目录与配置目录的表示并在 Windows 上忽略大小写；没有 `cygpath` 的环境按 `pwd -P` 做大小写敏感比较。大小写折叠使用 `tr`；若 `tr` 失败或被替换，守卫会回退到原始值（大小写敏感），不会退化为空模式匹配。
- `update` can set or replace `--cwd`, environment keys, and collections, but it cannot clear a working directory or remove an individual environment key.
- `import` preview opens a read-only SQLite handle against an existing database. That handle may leave `-wal` / `-shm` side files next to `aliases.db` even though no alias is persisted.
- Import preview cannot model every insert-time conflict. For example, `ConflictStrategy::Overwrite` case-fold persistence in PowerShell can behave differently when records are actually written, so preview counts are not a guarantee of the `--yes` outcome.
- The current revision is derived from alias rows and tombstone rows (`max(alias revisions, tombstone revisions, 1)`). If tombstone pruning is wired in later without a stored monotonic counter, the derived revision could regress relative to an already-applied revision.
- GUI visual layout, real-window interaction, keyboard focus, accessibility, and real terminal behavior remain manual acceptance items. Frontend unit tests, type checking, and a successful build do not prove those qualities.
- Package upgrade and rollback (test-matrix case L-019) is a package-level concern and remains a manual acceptance item. The CLI does not implement an installer, upgrade, or rollback flow.
- The wizard's whitespace warning is heuristic. It distinguishes a path with spaces from a program plus arguments using the last extension-bearing token, interpreter names, flag tails, and path separators. An extensionless path with spaces followed by an argument, or a filename that looks like an interpreter, remains inherently ambiguous and may be misclassified; the warning is advisory and never rewrites the record.
- Automatic Shell detection cannot be guaranteed complete. `PATH` differences, Microsoft Store aliases, portable builds, shells installed after the process starts, custom launchers and WSL can all be missed. `detect_shells` therefore always returns all four supported shells, reports `not_found` rows, and allows `shells.executables.<shell>` plus a profile override. A configured but missing executable is reported as not detected rather than silently using another installation. If `PATH` resolves Bash to the WSL launcher, known-path scanning continues so a native Git Bash/MSYS2 installation wins; WSL is reported only when no native candidate exists.
- Version probes are bounded at about two seconds and are best-effort. Output is read on a worker thread so a grandchild process that inherited the stdout pipe cannot extend the deadline; the probe result is still reported as unknown. A timeout, non-zero exit or unreadable output leaves the version `None`; it does not change the detected flag. WSL bash is deliberately not launched for a probe, so its version is always unknown from the Windows side.
- Bash/Zsh default to `$HOME/.bashrc` / `$HOME/.zshrc` (Windows `%USERPROFILE%`). When no home directory is available, setup requires an explicit absolute profile path. Older releases wrote `<config-root>/.bashrc` / `.zshrc`; those paths are now only uninstall candidates, not install/status targets.
- Shell path overrides (`shells.executables` and the four profile paths) must be absolute. A leading `~` is expanded from `HOME`/`USERPROFILE` on config load and in interactive prompts; other relative paths are rejected with a configuration error. `~user` is not expanded. `shell install`, `shell uninstall` and non-interactive `doctor` reject empty/non-absolute configured profile paths (doctor reports `config_invalid` and still exits 0), while full `uninstall` intentionally still considers the configured path plus legacy/default candidates for loader cleanup.
- Existing installations upgrade with an empty `shells.enabled`. Nothing is auto-enabled, so `add`/`update` intentionally return `ShellNotReady` (exit 12) until the user runs `aliasmgr doctor` once and confirms the shells to enable.
- A WSL bash row can be handled manually by entering a native Windows executable (for example Git Bash) and its profile/RC path, or by running `doctor` inside the distribution. Alias Manager never writes a Windows profile for the WSL launcher itself.
- `shells.enabled` and `shells.executables` are user intent, not proof that a Shell is usable. Enabled does not imply detected, and a loader block existing does not prove the current terminal has loaded it. `doctor` distinguishes detected, enabled, loader-valid and current-session state; the last remains unknown.
- `add`/`update` preflight checks only the record's target shells. It verifies the enabled intent and (unless `--no-sync`) the loader block; it does not execute the per-shell executable or prove that a new terminal will load the file. `--allow-missing-loader` intentionally saves records that will not take effect yet.
- Auto-sync runs after the database commit. If one or more affected shells fail, the write is not rolled back and the CLI exits with `PartialSync` (10) after listing the failures. `--no-sync` and `runtime.auto_sync=false` skip the sync entirely; a later `sync`/`doctor` is required. A confirmed `import --yes` also syncs all referenced shells once (or honors `--no-sync`/`runtime.auto_sync`), while import preview never syncs. Auto-sync does not reload or restart an open shell.
- `shells.executables` affects detection only. Sync's optional syntax check still invokes `bash`/`zsh`/`powershell`/`pwsh` by name on `PATH`, so a non-standard executable can be detected while syntax checking remains a documented no-op.
- Nested unknown keys under `[shells]` (including unrecognized `[shells.executables]` entries) are not preserved by struct deserialization; validation rejects unsupported `enabled`/`executables` spellings on save. Existing profile-path overrides and unknown top-level keys are preserved as before.
- The interactive `doctor` screen is a CLI flow built on the existing terminal primitives. Unit tests cover detection, planning, the line-based fallback and non-TTY dispatch; real-terminal behaviour (raw mode/alternate screen restore, resize, ConPTY/mintty differences, PS 5.1/pwsh and Bash/Zsh PTYs) remains a manual/PTY acceptance item.
- The GUI now uses the shared first-run/setup APIs: it lists all four shells, previews the target and marked block, installs the loader only after confirmation, and reports per-step config/loader/sync results. Setup results stay visible in the startup banner until acknowledged, including loader-install and sync failures. The TUI embeds the same shared setup state machine for first-run, startup repair, the settings panel and the add/edit preflight.
- The GUI full wizard is shown only when `config.toml` does not exist. Choosing **Skip for now** writes an empty `shells.enabled`, so later launches show a compact "not configured" notice instead of the wizard. If the configuration already exists but no shell is enabled (for example an upgrade), only the compact notice is shown; users open the Settings shell panel to enable shells. This is deliberate and is not a second configuration source: the shared `config.toml` is the only persisted state.
- GUI startup re-detects all four shells (bounded version probes) and reports enabled shells whose executable is missing or loader is invalid, plus newly detected non-WSL shells. Dismissing a new-shell prompt records the current executable in `shells.seen`; disabling a shell records it too, so the same installation is not re-offered on every launch. A reinstall or different executable path prompts once again. The invalid-loader "Ignore for now" action remains session-only; "Disable" persists `shells.enabled`. Nothing is enabled automatically.
- GUI save preflight is strict and has no `--allow-missing-loader` equivalent. A save whose target shell is disabled or whose loader is not verifiable writes nothing, keeps the wizard draft, and offers the shared shell setup flow. Detection is not part of preflight: a shell whose executable disappeared after being enabled can still pass if its loader block verifies, matching the CLI rule, though startup reports it as needing attention.
- GUI shell toggles are per-shell and re-read the shared configuration before saving, so a shell enabled by the CLI/TUI or another GUI action is not dropped by a stale list. The Settings editor can clear a stored executable/profile override with an explicit "use default" action (`CLEAR_OVERRIDE` sentinel); blank fields alone still mean "leave the override unchanged".
- The GUI backend uses `#[tauri::command(async)]` for detection, CRUD, setup, import and sync commands so probes and file/database work run off the UI thread. The frontend loads startup shell status once and shares it with the Settings panel and alias wizard instead of re-probing on mount; the Settings panel adopts each refreshed snapshot (unless its editor is open or an action is running), and rescan/preview still perform fresh work on demand. A shell-status startup failure shows a compact retry notice instead of disappearing.
- GUI auto-sync runs once after a successful database write: old ∪ new shells for create/update, the record's shells for delete/toggle, and all referenced shells for a confirmed import. It returns per-shell results and reload commands; partial failures and missing loader blocks are shown as warnings and never reported as success. The command completes before the UI continues, so a slow sync keeps the save button busy rather than updating the database invisibly in the background. Import preview never syncs, and `runtime.auto_sync = false` skips it.
- The GUI does not reload the current terminal, restart the shell, modify environment variables/registry, or write anything outside the marked loader block. "Current session loaded" remains unknown and is never displayed as active.
- Loader install/uninstall re-reads the profile immediately before writing, so edits made before that read are preserved. A small race window remains between the final read and the write; simultaneous edits to the same profile can still overwrite each other. Alias Manager does not lock shell profiles.
- Default PowerShell profile resolution is path-based (`%USERPROFILE%\Documents\...` or `~/.config/powershell/profile.ps1`) and does not query the Windows known-folder API. A OneDrive-redirected Documents folder therefore requires setting `shells.powershell5_profile_path` / `shells.powershell7_profile_path` explicitly.
- The TUI is a terminal front end, not a new source of truth. It caches a database snapshot for rendering and re-reads on refresh/actions; the SQLite database and generated files remain authoritative. A TUI process and a CLI/GUI write are serialized by SQLite and the sync lock, but the TUI does not hold a long write transaction.
- The TUI never reloads the current shell. After saving it reports that sync is needed; after syncing it shows the per-Shell reload command and explicitly states that reload is still required. The fourth status layer ("current shell") is always unknown.
- The TUI full first-run wizard is shown only when `config.toml` does not exist and `shells.enabled` is empty. `q`/skip writes an empty `shells.enabled`, so later launches show a compact "not configured" status instead of the full wizard. An existing configuration with no enabled shell also shows only the compact notice; the settings shell panel is the path to enable one. No shell is ever enabled automatically.
- TUI startup detection runs in a read-only background thread with the shared bounded version probes. Enabled shells whose executable disappeared or loader is missing/invalid produce a one-time notice: `Enter` repairs, `i` ignores for the session, `d` persists `enabled=false`. Newly detected non-WSL shells can be set up once or dismissed persistently through `shells.seen`; a changed executable path prompts again. `Esc` closes a notice for the session only.
- TUI add/edit preflight is strict and has no `--allow-missing-loader` equivalent. It uses the shared `shell_readiness_problems` rule (enabled intent plus verifiable loader) before the database write; a blocked save keeps the draft and opens the same setup screen. Imported `fish`/`posix_sh` targets are ignored by preflight like the other front ends.
- TUI auto-sync after a successful write runs on the existing Jobs worker and core sync lock. It starts only when no other job is running, synchronizes once (old ∪ new for updates, the record's shells for delete/rename/toggle, all referenced shells for a confirmed import), and never rolls back the database on a sync failure. Import preview never syncs. The current terminal is never reloaded.
- The TUI path-override editor accepts absolute paths and `~/...`; a blank field is not a "clear override" action. Clearing stored executable/profile overrides is explicit (`c` in the shell panel), which previews platform defaults and persists the core `CLEAR_OVERRIDE` sentinel only after confirmation.
- The TUI masks environment values as `***` in the editor list and detail pane and redacts every value before rendering a generated preview. Values are only shown while the user explicitly edits one value. Keys remain visible.
- The TUI import/export uses core `transfer`; Ask and Skip both skip conflicts (there is no per-conflict prompt), Overwrite updates exact-name rows but skips PowerShell case-fold conflicts that need manual resolution, and export always covers all aliases (no selection).
- TUI settings preserve unknown top-level config keys and shell path overrides, but unknown keys nested inside known config tables are dropped by core struct deserialization. `runtime.default_shell` and `runtime.allow_relative_paths` are shared config values; the current CLI/TUI behavior does not gate on them, and `runtime.language` is persisted for the GUI but does not localize CLI output or the TUI (which stays English). The config directory is fixed at startup.
- The TUI does not implement bulk multi-select or `uninstall`. Loader install/repair and enable/disable are available through the first-run/settings shell panel; advanced loader removal remains `aliasmgr shell uninstall` with the CLI.
- The TUI search field searches all fields. Tag filtering and sorting are available; selecting a single search field is not.
- Real-terminal behaviour (raw mode/alternate screen restoration, resize, Ctrl+C, CJK font width, colour fallback, Windows Terminal/ConPTY/mintty differences) is not proven by `TestBackend` tests. Windows PowerShell 5.1/pwsh and Linux Bash/Zsh acceptance remains manual. This implementation was built and tested on Windows only.
- The TUI requires at least 80x24. Below that it shows only a resize/exit message and ignores every key except `q`/`Ctrl+C`; it does not attempt a compressed layout or render invisible confirmation modals.
- Mouse input, clipboard integration, Nerd Font icons and emoji are deliberately unsupported. Terminal text can still be selected with the terminal's own selection mode.
- Terminal output can only be sanitized at the TUI boundary: control characters in stored values are replaced with `?`/spaces for single-line rendering, but a terminal or font may still display wide/CJK glyphs differently from `unicode-width`'s tables.
- A generated file left behind with no alias or tombstone (and a `shell_state`-only shell) is not a target of `sync`: `sync::referenced_shells` only covers alias-bound and tombstoned shells. The TUI header deliberately ignores such orphans instead of reporting a permanent "sync needed", and Doctor reports them with manual-removal guidance rather than an ineffective sync action.
- The TUI preview defaults to a per-alias definition, but `f` offers a whole-file fallback. In that fallback an unrelated alias with an invalid or missing target can make the preview unavailable with `target is missing: /srv/missing-tool` (the executable/target string, not the alias name) even when the selected record is valid.
- Atomic export/config writes use a same-directory temp file and rename. On Unix the temp is created with the existing target's mode when replacing (so it is never briefly more permissive than the file it replaces) and with the requested new-file mode otherwise; existing targets keep their mode, newly created exports use the process umask (normally 0644), and a newly created `config.toml` is 0600. The parent directory is fsynced after rename on Unix; Windows cannot fsync a directory with std APIs, so rename durability across power loss is not guaranteed there. Symlinked targets are resolved and written through; cyclic or over-64-hop chains are refused with an I/O error (`InvalidInput`, CLI exit 13) and never replace the link. On Windows the read-only attribute is preserved but explicit ACLs are not copied with std APIs (the temp inherits the directory ACL), so an existing target with a custom ACL may receive the directory ACL after replacement.
- The import preview's changed-file guard uses SHA-256 plus size/mtime. The SHA-256 is computed over the same bytes that are parsed, so confirmation hashes once before reading, checks the read bytes, and hashes again before the database transaction; a file changed between those checks is refused, but the check is not a filesystem lock, so an external writer could still race the final transaction.
- Writing through a Windows symlink needs the symlink privilege (Developer Mode or elevation). `windows_file_symlink_is_written_through_when_supported` prints an explicit `SKIP` line when creation is denied; set `ALIASMGR_REQUIRE_SYMLINK_TESTS=1` to make that failure fatal.
